# Балансировка по записанным сессиям игрока

**Дата:** 2026-11-03
**Связанные документы:** `simulation-harness-2026-11-03.md`, `simulation-harness-variant-e-plan-2026-11-03.md`
**Статус:** проект решения. Реализация не начата.
**Исходная идея:** записывать действия игрока (нажатия, покупки) и сессию в целом, воспроизводить их симулятором на seeded RNG, оценивать результат и по оценке корректировать баланс. Хранить всё в SQLite. Кнопка записи — внизу по центру экрана.

---

## 0. Резюме для нетерпеливых

Идея в целом рабочая и является правильным следующим шагом, но в предложенной форме содержит одну фундаментальную проблему и четыре инженерных.

**Фундаментальная:** «запись нажатий + seeded RNG» даёт точное воспроизведение **только пока код и баланс не менялись**. А цель — именно менять баланс. Как только формулы изменены, записанные уклонения перестают соответствовать миру: игрок уходил от снарядов, которые теперь летят в других местах. Прогон при этом не падает — он выдаёт правдоподобные, но бессмысленные цифры. Это худший вид ошибки: он выглядит как данные.

Отсюда главный вывод документа: запись должна быть **эталоном поведения**, а не **реплеем**. Реплей (open-loop) остаётся полезным, но только как валидируемый участок с явно измеренной границей применимости.

**Инженерные проблемы:** прогон поздней игры сегодня занимает минуты на один забег (без этого оценка невозможна в принципе); экономика деталей отключена в симуляции, хотя покупки — часть предложенной записи; метрики усреднены по всему забегу, поэтому кривую сложности измерить нечем; SQLite в браузере писать некуда.

Рекомендуемый вариант собран в §6 и §7.

## 2. Главная проблема: запись перестаёт быть валидной ровно в момент изменения баланса

### 2.1. Механика

Запись — это отклик игрока на мир. Мир зависит от seed и от формул. Схема «тот же seed → та же траектория» верна при неизменном коде. Меняем `hpScale` — и цепочка расходится:

```
hpScale выше → враг живёт дольше → их больше на экране
            → спавн идёт в другие тики
            → враги стреляют в других позициях
            → снаряды в момент T находятся не там, где были
            → записанное в момент T уклонение уходит в другую точку
            → игрок получает урон, которого в оригинале не было
            → HP ниже → агент/игрок меняет поведение дальше
```

Расхождение нелинейно и нарастает: в `compare` мы уже видим по `rngDraws`, что число бросков меняется — значит траектории расходятся **сразу**, а не «постепенно к концу».

### 2.2. Почему это опаснее, чем кажется

Прогон с устаревшей записью не выдаёт ошибку. Он выдаёт `damageTaken = 41.2` вместо `9.3`, и это выглядит как «станет тяжелее». По такой цифре можно уверенно принять неверное решение и даже закоммитить baseline. Единственная защита — явное измерение момента расхождения, а не вера в воспроизводимость.

### 2.3. Что от записи действительно устойчиво

| Тип оценки | Устойчив к смене баланса? | Комментарий |
|---|---|---|
| Реплей осей (open-loop) | **Нет** | Валиден при регрессии движка и в стендах, где мир почти не меняется (TTK, дуэль) |
| Реплей как префикс + агент дальше | Частично | Открытая часть признаётся недействительной после `firstDivergenceTick` |
| Запись как эталон для калибровки агента (closed-loop) | **Да** | Агент играет в новом мире сам, параметры взяты из записи |
| Запись как набор стартовых условий (мета-состояние, арсенал, волна) | **Да** | Не зависит от траектории |
| Профилировка навыков (время реакции, точность прицела) | **Да** | Это параметры человека, а не мира |

Практический вывод: из записи берём **три вещи** — стартовое состояние, профиль навыков и короткий валидируемый префикс. Не берём длинную траекторию как основу оценки.

### 2.4. Что говорит в пользу исходной идеи, несмотря на это

Для части задач реплей валиден и очень дёшев:

- **регрессия движка/рефакторинга** — баланс тот же, код другой, расхождение = баг;
- **отладка** — «вот этот конкретный забег, где я умер на 47-й секунде»;
- **стенды TTK** — 1–2 врага, 10 секунд, мир почти не успевает разойтись;
- **приёмка правок, которые по построению не влияют на траекторию** (косметика, звук, рендер).

Именно поэтому реплей не нужно выбрасывать — нужно перестать ждать от него оценки баланса.

## 3. Проблемы

| # | Проблема | Почему блокирует |
|---|---|---|
| **P1** | Запись невалидна после изменения формул (§2) | Без решения оценка баланса по записи даёт уверенно неверные цифры |
| **P2** | Симуляция медленнее игры примерно в 8 раз (480 тиков/с против 60×6 = 360 тиков/с реального времени в один поток, но на практике один забег до волны 20 — 75 с) | Баланс — это итерации. 3 часа на одну итерацию = «попробуем потом» |
| **P3** | Экономика деталей выключена (`testMode: true`), а покупки — часть предложенной сессии | Невозможно оценить ни цены апгрейдов, ни смысл покупок между забегами |
| **P4** | Метрики усреднены по забегу: одна цифра DPS + `waveReached` максимумом | Кривую сложности измерить нечем: «13.2 DPS за 120 с» — это смесь волн 1–4 |
| **P5** | Агент не видит пикапов (`PlayerView` их не содержит) | Прогресс внутри забега (подобрал оружие → стал сильнее) отсутствует; в записи человек к пикапам летит |
| **P6** | Агенты не откалиброваны по человеку | `reactionTime`/`aimJitter` назначены вручную; вывод про «DPS» описывает OrbitAgent, а не игрока |
| **P7** | `compare` не сравнивает новые метрики (`waveReached`, `finalHp`, `damageTakenByKind`, `byKind`) | Уже сейчас `damageTakenByKind` считается и не попадает в отчёт о регрессиях |
| **P8** | `REGRESSION_RULES` трактует рост `survivalTime` как улучшение | В лейт-гейме рост выживаемости = «стало слишком легко», то есть правило переворачивает смысл |
| **P9** | SQLite из браузера недоступен без wasm/OPFS, а запись рождается в браузере | «Писать всё в SQLite» в лоб не реализуемо: нет общего файла у браузера и Node |
| **P10** | `node:sqlite` нет на Node 20 (`engines.node: ">=20"`, CI на 20) | Альтернатива — `better-sqlite3` с нативной сборкой: ломает `npm ci` на части платформ |
| **P11** | Бинарный файл БД в git: нечитаемый diff, merge-конфликты, невозможность ревьюить baseline в PR | Baseline — предмет ревью; в виде BLOB его не проверить |
| **P12** | Канвас целиком является тач-зоной (`touchstart` на canvas) | Кнопка «внизу по центру» поверх канваса перекрывает управление на мобильных и провоцирует случайные нажатия |
| **P13** | Нет формата сессии: забег зависит от мета-состояния (upgrades, weaponLoadout, droneLoadout, parts, bestWave) | Без полного снимка хранилища прогон невоспроизводим даже при неизменном коде |
| **P14** | Реальная запись времени (`performance.now`) не совпадает с тиками мира | Мир тикает фиксированно 60 Гц, ввод приходит в реальном времени: привязка «по времени» поплывёт |
| **P15** | Автокоррекция баланса без распараллеливания и без целевой функции | «Скорректировать баланс» = десятки прогонов на каждый кандидат; без цели оптимизировать нечего |

## 4. Идеи

### I1. Писать `PlayerIntent` по тикам мира, а не события ввода по времени

Снимать состояние `HumanControls` в начале каждого `world.tick` — в той же точке, где сейчас опрашивается агент. Формат записи — тот же `PlayerIntent[]`, который уже читает `ReplayAgent`.

Снимает P14 полностью и половину P13.

| Плюсы | Минусы |
|---|---|
| Формат уже существует и уже потребляется — `ReplayAgent` без изменений | Пишется «сырое намерение», а не исходные клавиши: нельзя переопределить раскладку задним числом |
| Нет привязки к wall-clock → нет дрейфа и проблем с частотой кадров | За пределами тиков информация о промежуточных нажатиях теряется (на 60 Гц незаметно) |
| Запись одинаково воспроизводится в браузере и в Node | Требует, чтобы запись шла через мир, а не через DOM-слушателей |
| Компактно и стабильно по объёму | |

**Оценка: обязательно.** Это фундамент всех остальных пунктов, и он почти бесплатный.

### I2. Дельта-кодирование записи

Писать запись только там, где намерение изменилось относительно предыдущего тика; остальное — длина повтора.

| Плюсы | Минусы |
|---|---|
| Типичная сессия сжимается в 5–10 раз (игрок редко меняет ось каждый кадр) | Декодирование чуть сложнее; нужна проверка целостности |
| Случайные прогоны (постоянно меняющиеся оси) сжимаются хуже — но они и не нужны | |

Ориентировочный объём без сжатия: 60 записей/с × ≈70 байт ≈ **0,25 МБ/мин**, десятиминутная сессия ≈2,5 МБ. С дельтой — 0,3–0,5 МБ.

**Оценка: полезно, но не сейчас.** 2,5 МБ на сессию приемлемо; оптимизировать стоит после того, как появится десяток сессий.

### I3. JSONL как источник истины, SQLite — как производный индекс

Запись и результат прогона — append-only JSONL (одна строка = одно событие/прогон), лежат в `sim-results/` и не попадают в git. SQLite строится импортом из JSONL по команде `sim index` и служит для запросов («все прогоны `agent=evade`, волна > 10, за месяц»). В git коммитятся только сводные baseline-отчёты в тексте.

| Плюсы | Минусы |
|---|---|
| Браузер может написать JSONL без wasm и без OPFS — снимает P9 | Две системы хранения вместо одной: нужна проверка, что индекс не устарел |
| Git-ревью baseline остаётся возможным (снимает P11) | JSONL дублирует данные, которых в SQLite меньше |
| SQLite остаётся там, где он силён: ad-hoc-запросы и агрегаты по истории | Нужна команда перестройки индекса |
| Формат можно читать `grep`-ом и отдавать в `compare` без прослойки | |

**Оценка: предпочтительный вариант хранения.** Прямое решение конфликта «браузер пишет / Node читает / PR ревьюит».

### I4. SQLite через `node:sqlite`, с деградацией

| Плюсы | Минусы |
|---|---|
| Без зависимостей, без нативной сборки | Нет на Node 20, а `engines` и CI именно на 20 → в CI индекс недоступен |
| Достаточно для локальной аналитики | Экспериментальный API: возможны изменения между версиями |

### I5. SQLite через `better-sqlite3`

| Плюсы | Минусы |
|---|---|
| Зрелый, быстрый, синхронный API | Нативная сборка: `npm ci` требует toolchain, ломает часть платформ и замедляет CI |
| Работает на Node 20 | Тяжёлая зависимость ради индекса, который — не источник истины (I3) |

**Оценка I4/I5: ни одна как обязательная.** При I3 индекс опционален: `node:sqlite` если доступен, иначе `--no-index` без ошибки. `better-sqlite3` появляется только если объём истории реально упрётся в производительность JSONL-сканирования.

### I6. Реплей как валидируемый префикс, а не как основа оценки

Прогон стартует с записанных намерений, но на каждом снимке сравнивает мир с эталонной записью. Как только `firstDivergenceTick` пройден, открытая часть помечается недействительной и дальше играет агент. В отчёт попадают: длительность валидного префикса, доля тиков, закрытая реплеем, и «источник» каждой метрики.

Снимает часть P1, превращая молчаливую ошибку в явное число.

| Плюсы | Минусы |
|---|---|
| Ошибка воспроизведения становится измеряемой величиной | На сильных правках баланса префикс коротким будет нулевым — то есть польза падает ровно там, где она нужнее |
| Дёшево: механизм расхождения (`Snapshot`, `firstDivergence`) уже есть | Нужно хранить эталонные снимки вместе с записью, не только намерения |
| Даёт точный инструмент для регрессии движка и отладки | Усложняет модель прогона «часть — реплей, часть — агент» |

**Оценка: да, но как инструмент диагностики, а не как метод балансировки.**

### I7. Калибровка агента по записи (closed-loop)

Из записи извлекаются измеримые характеристики человека — медианное время реакции на резкую смену курса, точность удержания прицела на цели, доля тиков с огнём, предпочитаемая дистанция до цели, частота и триггеры способности, поведение у края зоны. Они становятся параметрами существующих агентов (`reactionTime`, `aimJitter`, `fireCone`, `fireRange`). Агент, собранный так, играет в **новом** мире сам.

Закрывает P1 и P6.

| Плюсы | Минусы |
|---|---|
| Устойчиво к изменению формул: агент реагирует на текущий мир | Это уже оценка через модель игрока, а не через самого игрока: погрешность модели переходит в вывод |
| Даёт многократное усиление: одна запись → сколько угодно прогонов на разных seed | Нужна проверка, что калиброванный агент действительно похож на запись (метрика сходства) |
| Все параметры уже есть в `AgentParams` — менять архитектуру не нужно | Поведение у пикапов не воспроизведётся без P5 |
| Позволяет держать «слабого/среднего/сильного» пилота из реальных людей, а не из головы | Одна запись = один человек; нужна выборка, иначе калибровка подстроится под стиль одного игрока |

**Оценка: центральная идея рекомендуемого варианта.** Именно она превращает запись из хрупкого реплея в работающий инструмент.

### I8. Запись как набор стартовых условий (без траектории)

Из сессии берутся только мета-состояние (upgrades, weaponLoadout, droneLoadout, parts, bestWave), seed, стартовая волна и арсенал. Дальше — обычный прогон с агентом.

| Плюсы | Минусы |
|---|---|
| Полностью устойчиво к смене баланса | Теряется индивидуальность игрока: это тот же агент, но с «человеческим» стартом |
| Реализуется на существующем `scenarioStorage` — минимальная работа | Не проверяет покупки «в динамике», только их результат |
| Позволяет строить сетку «сборка × волна» — самый нужный для баланса срез | |

**Оценка: да, дешёвый и полезный первый шаг.** Хороший способ начать получать пользу от записей до готовности I7.

### I9. Распараллеливание прогонов по seed через `worker_threads`

Прогоны полностью независимы: каждый создаёт свой мир, `resetGameEntityIds()` уже вызывается на создание мира, глобальное состояние между прогонами не передаётся (проверено само-тестом на 10 повторов).

Снимает P2: 6 ядер → ориентировочно ×4–5 практически → сетка из 100 seed до волны 20 за ~25 минут вместо 2–3 часов.

| Плюсы | Минусы |
|---|---|
| Самый большой выигрыш на единицу усилий | Нужен переносимый сериализуемый результат (метрики — плоские числа, снимки — строки-хэши, проблем нет) |
| Не меняет игровую логику и не трогает детерминизм | Пул воркеров усложняет CLI и отчёт о прогрессе |
| Делает возможными I10 и I13 в принципе | На малых сетках (3–5 seed) распараллеливание не окупается |

**Оценка: обязательно, до всего, что требует длинных прогонов.** Без этого остальные пункты бессмысленны практически.

### I10. Метрики с разбивкой по волнам

`MetricsSink` ведёт бакеты по `waveOrchestrator.wave`: урон нанесённый/полученный, убийства, время в волне, минута жизни, `finalHp` на входе/выходе волны, источники урона.

Снимает P4.

| Плюсы | Минусы |
|---|---|
| Появляется сам объект балансировки — кривая, а не среднее | Формат результата перестаёт быть плоским, нужно обновить `RunResult`, таблицы, `compare` |

## 7. Вывод: что предпочтительнее и почему

**1. Из исходной идеи главное надо заменить, а не реализовать: запись — эталон, не реплей (I7 вместо наивного реплея).**
Это единственный пункт, без которого вся схема не работает по назначению. Запись нажатий воспроизводится точно ровно до первого изменения формул, а изменение формул — и есть цель. Поэтому запись используем для калибровки агента: из неё извлекаются время реакции, точность прицела, дистанция, привычка стрелять и поведение у границы зоны — всё это уже есть в `AgentParams`. Агент, собранный из реальной записи, играет в изменённом мире сам и потому даёт оценку, устойчивую к правкам баланса. Отказываться от реплея не нужно (I6), но его роль — диагностика движка и отладка, а не балансировка.

**2. SQLite не должен быть источником истины (I3 вместо I4/I5).**
Запись рождается в браузере, а браузер не пишет в SQLite-файл без wasm/OPFS (P9); `node:sqlite` нет на Node 20 из `engines` и CI (P10); бинарный файл нельзя ревьюить в PR (P11). Отсюда: источник истины — JSONL (пишется и в браузере, и в Node, читается `grep`-ом, дружит с `compare`), а SQLite — опциональный локальный индекс для запросов по истории, с деградацией на `node:sqlite`. `better-sqlite3` с нативной сборкой не нужен: он решает задачу, которую мы решили форматом.

**3. Первым делом — не запись, а распараллеливание и разбивка по волнам (I9, I10).**
Именно они определяют, будет ли инструмент использоваться. Сейчас итерация оценки стоит 2–3 часа в один поток; ×5 на шести ядрах и бакеты по волнам превращают её в 25 минут и дают измеряемый объект — кривую, а не среднее по забегу. Запись без этого даст красивые, но усреднённые цифры по волне 4, тогда как баланс правится на 15–25-й.

**4. Покупки из предложенной сессии имеют смысл только вместе с экономикой (I11, P3).**
Сейчас доход деталей в симуляции выключён (`testMode: true`), поэтому «записать покупки и оценить» невыполнимо: оценивать нечего — детали не копятся. Включение экономики обязательно, но после I9/I10, иначе нечем прогонять цепочку «забег → покупка → забег».

**5. «Скорректирует баланс» стоит понизить до «посоветует» (I13).**
Автопилот меняет код игры по критерию, которого пока нет (§5). Прагматичный вариант — измерение чувствительности и поиск по сетке с выдачей кандидата: человек видит «`hpScale` +2% → выживаемость на волне 15 −4,1%» и решает сам. Это даёт почти всю пользу автокоррекции без риска оптимизации не под ту метрику.

**6. Кнопку — не вниз по центру (I14).**
Низ канваса занят тач-управлением, поэтому предложенное размещение мешает игре на телефоне. Горячая клавиша плюс индикатор в верхней панели, кнопка — в dev-оверлее.

**Порядок, в котором идеи окупаются:** I1 → I9 → I10 → I15/I3 → I8 → I12 → I7 → I11 → I16 → I6 → I13. Первые три шага (формат записи, распараллеливание, разбивка по волнам) — те, без которых последующие не имеют смысла; они же почти не рискуют существующим поведением.

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Калиброванный агент похож на запись, но не переносится на новый баланс | Средняя | Метрика сходства из шага 7; проверка плавности отклика на `hpScale` доверием к выводам |
| Одна запись = один стиль игрока | Высокая | Несколько записей; агрегат по людям; не калибровать баланс по одному человеку |
| Распараллеливание внесло недетерминизм | Низкая | Существующий тест «10 повторов идентичны» + сравнение параллельного и последовательного прогонов |
| Экономика после включения `testMode` меняет поведение агентов | Средняя | Включать точечно, сценариями; baseline переснимать с явной причиной |
| Baseline переснимается «чтобы стал зелёным» | Высокая | В комментарии к коммиту — обязательная причина; в `compare` предупреждение при смене `scenarioHash` |
| Целевые метрики (§5) выбраны неверно → рекомендации вредят | Средняя | Рекомендатель ничего не применяет сам; значения пересматриваются после первого же цикла |
| Запись влияет на производительность кадра | Низкая | Буферизация, сброс частями, запрет записи в prod-сборке |
| Объём `sim-results` разрастается | Низкая | Дельта-кодирование (I2) по факту необходимости; ротация локально, в git не попадает |

## 10. Что не делать

- Не строить автокоррекцию баланса, пока не заполнен §5.
- Не делать SQLite источником истины и не тянуть нативную зависимость ради индекса.
- Не писать запись через DOM-события с `performance.now()` — только намерения по тикам мира.
- Не считать валидацию баланса коротким реплеем: он не переживает правку формул (§2).
- Не размещать кнопку записи поверх канваса.
- Не включать `testMode` глобально: только по сценарию.
- Не менять боевые константы в PR с инфраструктурой записи.
